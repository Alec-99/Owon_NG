# UI-001 — Build the modular oscilloscope UI foundation

**Assigned to:** Codex  
**Phase:** UI only  
**Priority:** First development batch  
**Base branch:** \`feat/first-ux-prototype\` until prototype PR #1 is merged  
**Task branch:** \`codex/UI-001-app-foundation\`

## Objective

Convert the stand-alone \`prototype/index.html\` concept into a maintainable, polished desktop-first UI that will later support professional PicoScope-quality automotive/electronics workflows. **Do not implement USB integration or real device drivers, decoders, high-energy test capabilities, or diagnostic verdicts in this batch.** Do not claim PicoScope hardware equivalence.

Read \`AGENTS.md\`, \`docs/START_HERE.md\`, \`docs/UI_SPEC.md\`, \`docs/ROADMAP.md\`, \`docs/REFERENCE_REPOS.md\` and licence rules first. Inspect existing files/CI; research related open-source instrument projects and record relevant findings before coding.

## Deliverables

1. **Modular frontend foundation** — Use TypeScript and a lightweight, well-supported frontend/build setup (Vite recommended). Split layout/navigation, waveform renderer, controls, state, help, profile models, fixtures and local persistence into logical modules. Record any significant framework/renderer choice.
2. **Professional application shell** — Responsive desktop-first navigation for *Automotive, Elektronica, Vrij meten, Bibliotheek, Opnames/Geschiedenis, Rapporten, Instellingen, Help*. All screens render useful empty/demo states rather than blank placeholders.
3. **Usable scope screen** — Central waveform display, configurable visible CH1/CH2, independent scale/config control surfaces, timebase, simulated run/pause/single, trigger display, cursors, zoom/pan and simulated measurement readouts. Control actions should cause observable, coherent UI changes. If a control is not yet supported, label it **'nog niet beschikbaar in demo'** and explain why.
4. **Sample-guided workflow** — At least one end-to-end clickable automotive example (inductive CKP or narrowband O2) and one electronics example (PWM). Navigate from component/test selection through instructions, safe connection warnings, preset, synthetic reference, cursors/notes and demo save/export.
5. **Help system** — Information button on important settings: brief accessible explanation plus expandable technical version, in Dutch. Safety info is never hidden behind an optional info click.
6. **Demo capture state** — Differentiate synthetic, imported and prospective hardware sources in the types and visible status. Preserve or improve the ability to export/reopen simulated sample data and show correct origin; a local-only demo implementation is sufficient.
7. **Basic testing/CI** — Unit tests for fixture determinism and any calculations/mapping added; browser-level smoke checks covering navigation, automotive/electronics setup, cursor interaction, help, provenance and responsive layout. Integrate build/test with GitHub Actions.
8. **Documentation** — Update README with setup/dev/build/test commands and a truth table of working UI vs mocked vs future. Update decisions and third-party provenance for any borrowed code.

## UX targets

- Clear hierarchy: waveform in focus; sidebars and toolbars easy to discover.
- Strong readable contrast, responsive spacing and useful mobile/narrow viewport behavior.
- Keyboard shortcuts for simulation pause/run, access to menus and focus navigation; no keyboard traps.
- Distinguish selected vs disabled vs destructive actions. Show source badge **DEMO** at all times in simulated mode.
- Basic/expert explanation levels must exist at least for key waveform controls.
- No design copying from PicoScope. Reuse permissible external code only when licence/NOTICE conditions are fulfilled and documented.

## Exclusions

- Do not add USB device support, hardware test scripts, proprietary binary firmware, auto calibration or a real-time hardware acquisition engine.
- Do not build all guided sensor profiles to diagnostic completeness (UI-002).
- Do not start implementing DSP/protocol decoders/automated fault detection (post-UI phases).
- Do not remove the original \`prototype/index.html\` before the new app and tests replace its demo journey.
- Do not change the repository's licence without owner approval.
- Do not merge PRs.

## Acceptance checks

- Fresh checkout can run app locally with documented commands and without a scope attached.
- Navigation covers all required screens; no main navigation entry is a dead end.
- Switching Automotive and Electronics changes profile context; selecting CKP or PWM shows a corresponding explicitly synthetic trace and guided instructions.
- Run/Pause/Single controls provide consistent **demo** state, cursor and zoom operate on displayed samples; changes are not mere cosmetic buttons.
- Help buttons provide correct, understandable explanations; shared-ground warning is prominent.
- Data exports identify simulation and can round-trip through import, or clearly explain an explicit UI-001 limitation with a tracked follow-up.
- New automated tests pass locally and in CI; report commands/results and screenshots or reproducible screen observations.
- PR details what works, what is mocked and what remains for UI-002/UI-003.
